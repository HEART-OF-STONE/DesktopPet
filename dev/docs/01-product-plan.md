# DesktopPet 产品规划

日期：2026-09-15。本文是建议方案，不代表已实现功能。

范围更新：用户要求覆盖参考项目的 Agent 联动和余额能力，已将 Codex 用量/额度、任务反馈及余额看板提升为 V1 核心工作；以 `06-agent-integration.md` 为准。下文将状态信息排在后续的初始安排已被此项更新取代。内置 AI 聊天和 Live2D 仍保持后续阶段。

## 1. 产品方向

**一个住在桌面上的伙伴：有自然的小动作，能回应触摸，记得少量共同经历，在合适的时候提供帮助。**

核心顺序：陪伴感 → 日常使用价值 → AI 能力 → 可扩展生态。

已经确认的偏好：陪伴互动为主，逐步加入 AI 和实用工具。**V1 同时支持静态图片加程序变形、逐帧 2D；Live2D 在后续版本实现。**

本计划暂按以下假设制定，可在开工前调整：

- Windows 11 x64 首发；其他 Windows 版本、ARM、macOS 和 Linux 后续单独验证。
- 初期由一位开发者推进，同一时间显示一个活动实例；准备静态与逐帧示例包验证切换，可共用同一角色形象。
- 无账号也能使用基础陪伴与本地提醒；联网功能由用户启用。
- V1 的静态与逐帧渲染器共用动作接口；后续通过新增适配器接入 Live2D。
- 第一阶段不建设账号服务、商城、云同步或第三方代码插件市场。

首个体验闭环：启动见到角色 → 拖动和摸头得到回应 → 开启专注计时 → 角色安静陪伴 → 计时结束给出反馈 → 关闭后再次打开仍记得设置。

## 2. 参考项目：借鉴什么

参考 [DeepSeek Balance Whale Widget](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget)。已阅读仓库说明、包配置、挂载声明，以及前后端入口的部分源码；未运行或完整审计项目。

项目当前是 DSH Web 插件。值得借鉴的体验包括拖动吸附、按压弹性、自定义气泡、角色图片切换，以及余额和用量提醒。[仓库说明](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget#readme)

### 已核实的角色实现

**默认角色是静态 PNG + CSS/JavaScript 变形动画，不是 Live2D，也不是用一套角色图片逐帧播放来实现按压效果。**

- 默认角色文件是 `assets/DSniang1.png`，备用图为 `DSniang02.png`。
- 前端用普通 `img` 元素显示角色。
- 按下时执行 `scaleY(0.88) scaleX(1.05)`，松开恢复到 `scaleY(1) scaleX(1)`，配合 CSS 贝塞尔过渡产生弹性回弹。
- 贴左时使用水平镜像；气泡由 SVG 与网页元素绘制。
- 仓库另有 `rua.gif`、`bubble-petpet.gif` 等动图，用于气泡/辅助内容；这与角色本体的实现分开。
- 检查的完整仓库文件树未包含 `.moc3`、`.model3.json` 等模型资源，包配置未声明 Live2D SDK 依赖。

证据：[角色创建与图片加载](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget/blob/main/assets/whale-widget.js#L573)、[按压与松开变形](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget/blob/main/assets/whale-widget.js#L11865)、[资源目录](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget/tree/main/assets)。核对日期为 2026-09-15，前端文件 blob SHA 为 `4e4938c97828250ea2a1548423aa34f449a4b472`。

这为本项目提供了更轻的起点：如果首版只追求同样的拖动、按压、弹跳和换图效果，一张透明角色图就可以验证主要交互，不需要先准备逐帧动画或 Live2D 模型。

| 参考能力 | 本项目中的转化 |
|---|---|
| 按压反馈与音效 | 点击、摸头、拖起、落地时各有动作，音量统一控制 |
| 拖动和边缘吸附 | 吸附显示器可用边缘，支持缩放与位置恢复 |
| 可编辑气泡 | 台词、提醒、AI 回复共用显示和排队机制 |
| 自定义角色 | V1 使用统一角色包支持静态图与逐帧动画，后续扩展 Live2D |
| 余额提醒 | 后续做成一个可关闭的功能模块 |

从网页挂件到独立桌宠还需要：透明原生窗口、系统级鼠标穿透、托盘、焦点管理、多显示器、休眠恢复和安装更新。现有宿主路由、凭据服务及页面注入方式不能直接当作独立应用的底座。[包配置](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget/blob/main/package.json)、[前端入口](https://github.com/MeteorNOX/DeepSeek-Balance-Whale-Widget/blob/main/assets/whale-widget.js)

## 3. 逐帧 2D 与 Live2D 的区别

Live2D 本身也属于 2D。这里的“逐帧 2D”指 PNG 序列、精灵图等图片动画；单张图片配合缩放、旋转也可作为最早期原型。

因此实际有三个层次：静态图 + 程序变形（参考项目的默认方案）、逐帧 2D、Live2D。后两种用于更丰富的动作或表情，不能把参考项目的弹性效果误当成逐帧动画。

| 比较项 | 逐帧 2D | Live2D |
|---|---|---|
| 工作方式 | 播放预先画好的连续画面 | 对分层立绘的网格、参数做实时变形 |
| 擅长的表现 | Q 版小动物、像素角色、跑跳和夸张动作 | 呼吸、眨眼、视线跟随、细腻表情、说话口型 |
| 大幅动作 | 可逐帧画出任意姿势，帧数多时绘制量大 | 取决于立绘拆分和绑定范围；复杂转身、跑跳仍要专项制作 |
| 制作流程 | 画图 → 逐帧动画 → 导出 | 分层立绘 → 网格与变形器 → 参数绑定 → 动作/表情 → 导出 |
| 首个可用角色 | 少量画面即可起步 | 需要可用模型；一张普通 PNG 不能直接当完整模型 |
| 追加表情 | 新增画面或图层组合 | 已绑定参数可复用；新结构仍需改模型 |
| 换角色 | 加载另一套图片和动作映射 | 加载另一整套模型及其动作、参数映射 |
| 换皮肤 | 替换动画资源，或切换预设服装图层 | 切服装部件、切参数、换匹配贴图，或换整套模型 |
| 程序复杂度 | 相对低，播放和命中区域容易控制 | 需接 SDK、模型生命周期、参数协调和图形资源管理 |
| 性能 | 随贴图大小和帧数变化 | 随网格、遮罩、物理和贴图变化；通常需要更多实时计算 |
| 适合当前项目的用途 | 桌面行为原型、轻量角色、复杂跑跳 | 强调表情、交流和角色感的陪伴形象 |

表中“擅长”“复杂度”是工程判断，不是绝对限制；复杂逐帧资源也可能比简单 Live2D 模型更耗内存。

### Live2D 换角色与换皮肤

**换角色完全可行。** 例如从猫娘切到鲸鱼娘，应用卸载旧模型、加载新模型，再把“开心、困倦、摸头”等通用动作映射到新模型支持的动作。

**换皮肤也可行，但皮肤需适配模型。**

1. 同一模型预制两套衣服：通过部件显隐或参数切换。
2. 同一模型换颜色、纹理：替换与原网格、贴图布局匹配的材质图片。
3. 发型、体型和服装结构变化很大：通常制作另一套模型，界面仍可把它展示成一款皮肤。

不能把任意服装 PNG 放进任意模型后就期待自动贴合。模型参数和部件透明度可由 SDK 控制，但具体可换装能力来自模型制作。[参数操作](https://docs.live2d.com/4.2/en/cubism-sdk-manual/parameters/)

运行时通常需要 `.model3.json`、`.moc3`、贴图，以及可选的动作、表情和物理文件；编辑工程与运行时导出文件要区分。[官方导出说明](https://docs.live2d.com/en/cubism-editor-manual/export-moc3-motion3-files/)

### 已确定的版本选择

V1 采用两种表现形式：

1. **静态图片加程序动画**：导入透明 PNG，提供按压变形、松手回弹、轻微摇摆、位移和左右翻转，复现参考项目的核心交互体验。
2. **逐帧 2D 动画**：按动作播放有序 PNG 序列或精灵图，支持帧率、循环、单次播放和动作切换。

两种形式共用桌面窗口、气泡、音效、拖动、角色管理、皮肤和本地计时。一个角色包声明自己的渲染方式；切换角色时自动选择适配器。

先完成静态图的桌面交互，再接入逐帧播放和资源管理，之后交付 V1。Live2D 的技术样例、SDK 接入、模型采购与导入能力全部移至 V1 之后；现阶段仅保持角色接口可扩展。

首版不要求两套完全不同的美术；可用同一形象的单张图和少量动画帧验证两种模式。缺少动作时降级为通用缩放反馈、气泡或待机动作；静态图不会凭空产生眨眼或口型细节。

### 后续 Live2D 阶段的发布条件

以下事项在启动 Live2D 阶段时核对，不作为 V1 开发与发布的前置条件。

需要分别核对：SDK 使用与发布条件、模型资源许可、制作工具许可。

官方允许在同意相应 SDK 条款后先进行开发验证；一般内容与“可扩展应用”的发布规则不同。[SDK 发布许可](https://www.live2d.com/en/sdk/license/)

官方将通过添加文件或数据使用不定数量模型等能力纳入“可扩展应用”的定义，且该类别要求发布前审核和专门协议，包含个人与小规模主体。因此，**允许用户任意导入 Live2D 角色的桌宠可能属于该类别**，应根据实际功能向官方确认。固定内置角色方案也需按其实际发布形式核对条款，不能仅凭“个人、免费、开源”推断豁免。[可扩展应用规则](https://www.live2d.com/en/sdk/license/expandable/)

规划上将开放 Live2D 导入列为独立发布节点；许可未确定时继续完成基础桌宠和逐帧角色，不将其作为已经承诺的公开功能。

## 4. 功能地图与分期

P0 = 第一个可日用版本必需；P1 = 基础稳定后加入；P2 = 验证需求后扩展。

| 模块 | P0：陪伴闭环 | P1：增强陪伴 | P2：扩展 |
|---|---|---|---|
| 桌面存在感 | 透明窗口、拖动、吸附、缩放、托盘、隐藏/找回 | 自动低打扰、更多显示模式 | 多宠物、跨平台 |
| 宠物行为 | 待机、开心、困倦、拖起、触摸反馈；逐帧包可提供眨眼 | 游走、轻量心情、互动日记 | 事件剧情、节日行为、小玩具 |
| 角色资源 | 静态与逐帧角色包、导入、预览、切换及匹配资源的皮肤 | Live2D 适配与模型能力映射 | 资源编辑器、创作者生态 |
| 气泡 | 本地台词、冷却、排队、关闭 | 图片模块、可编辑模板 | 条件台词、更多模块 |
| 实用工具 | 番茄钟或简单倒计时、结束反馈 | 待办、休息提醒、白名单快捷入口 | 日历、天气、剪贴板主动处理 |
| AI | 预留接口 | 文本聊天、流式回复、人设、可管理记忆 | 按键说话、朗读、主动触发的截图问答 |
| 状态信息 | 不作为首版必需 | 可选 API 余额与本应用用量 | 经验证的数据源、下载/构建结束事件 |
| 数据 | 本地保存、导出设置、恢复默认 | 对话删除、备份与迁移 | 可选云同步 |
| 可扩展性 | 内置模块与声明式角色包 | 模块开关、统一事件和动作接口 | 独立评估第三方执行环境与分发 |

不要用饥饿惩罚、死亡或连续签到负担来制造留存。心情主要用于反馈最近互动；离开几天再回来仍应得到友好回应。

## 5. 首版体验规格

### 桌面交互

- 单击：触摸反馈 + 短台词；设置移动阈值，避免拖动结束误触点击。
- 按住拖动：进入拖起动作；松开后吸附或停留，位置不越出可用屏幕。
- 右键：喂食/互动、专注计时、切角色、设置、隐藏、退出。
- 透明区域让鼠标操作落到后面的应用；角色本体可交互。
- 气泡会选择合适方向，贴边时不裁掉内容；文字保持正常阅读方向。
- 托盘保留“显示宠物”“移回主屏”“设置”“退出”，即使位置异常也能找回。

### 陪伴节奏

- 初始提供 6 个语义动作：待机、被摸、开心、困倦、拖起、庆祝。
- 首个素材包建议 20–30 条本地台词，并为重复台词设置冷却。
- 无操作时少量自然动作；不持续弹气泡、不抢输入焦点。
- 有手动专注/免打扰模式；全屏自动隐藏为增强功能，单独做平台验证。
- 低打扰模式下关闭声音与闲聊，只保留用户明确设置的提醒策略。

### 界面结构

1. 宠物窗口：角色与短气泡。
2. 快捷菜单：少量常用动作。
3. 工具面板：需要时打开，可收起；聊天随 AI 阶段加入。
4. 设置窗口：V1 提供外观、行为、提醒、数据与关于；AI 设置随对应功能加入。
5. 角色管理：预览、作者与许可信息、切换、皮肤和动作能力。

先实现常用设置，复杂气泡编辑器在功能验证后增加。

## 6. AI 与工具的产品边界

AI 用于生成语言、识别有限意图和选择已有表情。宠物的基础行为、计时和提醒由本地确定逻辑执行，断网仍可用。

示例：“陪我专注 25 分钟” → 识别倒计时意图 → 显示已启动的计时 → 角色进入安静状态 → 本地计时结束后庆祝。计时结果不能仅依赖模型说“已设置”。

第一批 AI 能力：

- 用户自行配置服务商和密钥；初期实现一个经过验证的服务商适配器。
- 文本聊天、停止生成、超时反馈、可选朗读接口。
- 人设可编辑；长期记忆先保存用户明确选择的称呼、偏好和事项。
- 记忆可查看、修改、删除；区分全局偏好与单角色经历。
- 费用预算限制在本应用可控制的请求内；本应用消费估算与账户余额分别显示。

后续工具：白名单应用启动、明确选择文本后的翻译、主动提交截图后的解释等。文件、剪贴板、麦克风、截图的访问都由实际功能入口说明范围，默认不持续收集。

## 7. 美术与内容需求

统一角色包中包含：角色名称、作者、许可、渲染类型、资源入口、动作映射、点击区域、气泡锚点、可选音效和皮肤。

第一套角色的验收重点：轮廓在深浅壁纸上都清楚、缩小仍好辨认、动作有反馈、循环不跳帧、贴边不切掉关键部位。

### V1 素材交付

- 静态角色：透明 PNG、预览、点击区域与气泡锚点；程序提供变形反馈。
- 逐帧角色：有序 PNG 帧列表，或 PNG 精灵图及帧矩形描述；定义各动作的帧率、循环方式、锚点和结束后动作。
- 两种模式都提供至少一个示例包；可以复用同一角色形象。
- 皮肤：静态角色替换图片；逐帧角色替换配套帧资源与动作映射。缺帧的皮肤应在导入时指出问题。
- 声音为可选资源；视觉反馈无需声音也应清晰。

### 后续 Live2D 素材交付

进入 Live2D 阶段后，委托或挑选模型前明确交付内容：

- 运行时导出包，以及是否需要可编辑源文件。
- 眨眼、呼吸、视线、口型的可控参数。
- 六个首版动作对应的动作或表情，允许少量通用反馈降级。
- 哪些衣服、配饰能够切换；需要新增模型的皮肤如何交付。
- 软件内展示、随安装包分发、修改和商业发布的许可范围。

美术报价受角色复杂度、动作和权利范围影响，当前不虚构固定价格。先确定一个角色的最小交付清单，再获取报价。

## 8. 发布与后续价值

首个公开版本优先验证：用户是否愿意长期保留在桌面、是否经常手动隐藏、最常使用的互动和工具是什么。

通过小范围试用访谈与用户主动提交的诊断信息评估，不把埋点和账号作为首版依赖。

可选后续方向：免费基础版、独立角色包、一次性高级功能、用户自备 AI 密钥。V1 的发布方式结合其素材成本和分发权决定；进入 Live2D 阶段后再核对其发布条件，云端 AI 订阅需单独测算推理、语音、带宽和维护成本。

## 9. 尚待决定的事项

- 第一个角色的形象：动物、Q 版人物或偏二次元立绘。
- 是否已有透明角色图和逐帧素材，静态与逐帧示例是否使用同一形象。
- 项目是个人使用、分享给朋友、公开开源还是商业发布。
- 可投入的开发时间、已有技术经验和美术预算。

这些事项影响素材和发布安排，不妨碍先验证透明窗口、交互与角色接口。
